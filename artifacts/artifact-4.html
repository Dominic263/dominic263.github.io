Matching the Method to the Problem — ML vs. Deep Learning

Introduction: An applied report that takes two real-world systems — customer churn prediction and diabetic retinopathy screening — and argues why each demands the approach it uses, and why swapping them would fail.

Description

Deep learning is routinely described as the more advanced form of machine learning, as though the choice between them were a question of sophistication. This report argues that the choice is a diagnosis, not a ranking. Deep learning is a subset of machine learning distinguished by one capability — it learns features directly from raw data instead of being handed features a human selected — and that single difference determines how much data a system needs, how much compute it costs, and whether anyone will be able to explain its output.

The report examines two examples from the course lesson. Customer churn prediction with a support vector machine is traced to its real-world use in telecommunications and subscription retention, where structured account data and the need to justify an intervention make traditional machine learning the correct choice. Image recognition with a convolutional neural network is traced to diabetic retinopathy screening, where raw retinal photographs and visual patterns too subtle to hand-code make deep learning the only workable approach. For each case, the report also makes the negative argument — why the opposite method would fail — which is where the real reasoning lives.

For the portfolio, I paired the written report with a visual companion page built around a hand-coded SVG diagram that puts both pipelines side by side, so the structural difference is visible in a glance rather than only argued in prose.

Objective

Created for the Workshop 2 assignment in AIML-500, which asked me to select two machine learning examples from the lesson — one specifically of deep learning — find a real-world application of each, and explain why that approach suits the problem while the other does not. Beyond the assignment, my objective was to move past definitions and demonstrate the judgment an AI practitioner is actually paid for: choosing the right tool for a problem's data, constraints, and accountability requirements.

Process

  1. Selecting the pair: I deliberately chose two examples that fail in opposite directions — structured tabular data against raw pixel data — so the comparison would isolate the variable that actually matters rather than comparing two similar problems.
  2. Grounding each in reality: I traced each example to a documented real-world deployment rather than a hypothetical, including the published clinical validation of deep learning for diabetic retinopathy screening.
  3. Building the negative case: For each application I worked out specifically why the alternative approach breaks — not "it would be worse," but the mechanism of the failure, such as an SVM treating a million pixels as unordered independent values with no spatial relationship.
  4. Writing and citing: I wrote the report in APA format with a comparison table and supported the technical claims with peer-reviewed sources, including research on why tree-based methods still outperform deep networks on tabular data.
  5. Designing the companion: I hand-coded the two-pipeline SVG diagram so the report's central claim — that the only structural difference is who performs the feature engineering — is legible at a glance.

Value Proposition

Unique Value

Knowing what deep learning is is table stakes; knowing when not to reach for it is the more valuable and rarer judgment. This artifact shows I can evaluate a problem on its actual constraints — data structure, data volume, interpretability requirements, operational cost — and defend a technical recommendation in both directions, including recommending the simpler tool when the fashionable one would add cost without accuracy.

Relevance

Organizations waste substantial money applying deep learning to problems that never needed it, and lose credibility deploying black-box models where a decision must be explained. The reasoning in this report is the reasoning that prevents both failures, and it doubles as a resource any reader can apply as a checklist to their own problem: do the meaningful features already exist, and can a person name them?
