When the Data Fights Back — A Field Guide

Introduction: A practical reference to the three data problems every machine learning project runs into — missing data, imbalanced classes, and drift — written for classmates and anyone starting their first real project.

Description

Most of what goes wrong in a machine learning project is not the model; it is the data. This field guide covers the three failures that cause most of that trouble, each built around a scenario I worked through in a course roleplay: missing data in a telecom churn dataset, imbalanced classes in fraud detection, and data and concept drift in a housing price model.

Each section is written the same way — what the problem looks like in practice, why the obvious fix is usually wrong, and what to do instead. The guide opens with a diagnostic table that starts from the symptom a person can actually observe ("accuracy is superb but the model never flags the thing you care about") and works back to the likely cause and the first move. Two hand-coded diagrams carry the ideas that are hardest to convey in prose: the accuracy trap, where a model scoring 99.8% catches zero fraud, and the silent decay of a deployed model after the world it learned has moved.

The guide is written deliberately as a resource for other people rather than as evidence of my own learning. My classmates will hit all three of these problems, and the point of a portfolio, per this course, is to be a resource site others can learn from — so I wrote the reference I wish I had been handed at the start.

Objective

Developed from the Workshop 4 data challenges roleplay, in which I worked through three scenarios with an AI coach: handling missing values, training on imbalanced data, and responding to drift. My objective in expanding those notes was to produce something with a life beyond the assignment — a guide a classmate could open mid-project, find their symptom in a table, and get an actionable answer. That meant organizing it around what someone observes rather than around textbook categories.

Process

  1. Working the scenarios: I reasoned through each of the three cases in the roleplay — telecom churn with missing fields, fraud detection with extreme class imbalance, and a housing model degrading after launch.
  2. Finding the trap in each: rather than listing techniques, I identified the specific wrong instinct each problem invites — deleting incomplete rows, trusting accuracy, and assuming a deployed model stays correct.
  3. Reorganizing around symptoms: I built the diagnostic table from the observable signal backwards to the cause, because in practice you notice the symptom long before you can name the problem.
  4. Designing the two diagrams: I hand-coded the accuracy trap comparison and the drift decay chart in SVG, choosing those two because both describe a situation where the numbers look fine and the system is failing.
  5. Grounding it in the literature: I connected each section to established sources — SMOTE for minority-class synthesis, the concept drift adaptation survey, Little and Rubin on missing data, and the hidden technical debt paper on post-deployment maintenance.

Tools & Technologies Used

  • Machine learning data preparation concepts (imputation, resampling, class weighting, threshold tuning)
  • Evaluation metrics (precision, recall, F1, precision-recall AUC, confusion matrix)
  • Model monitoring and retraining concepts (data drift vs. concept drift)
  • HTML & CSS (the guide, consistent with this portfolio's design system)
  • Hand-coded SVG (both diagrams drawn as code)
  • GitHub Pages (public hosting, free to share)

Value Proposition

Unique Value

Explaining a technique proves you studied it; explaining the trap proves you understand it. Each section of this guide is built around the plausible wrong answer — why deleting incomplete rows can erase the exact pattern you are predicting, why the higher-accuracy model is the useless one, why a model can decay without a single error appearing in the logs. Producing this also demonstrates that I can write documentation other people can act on, which is a distinct and undervalued skill in technical teams.

Relevance

These three problems are close to universal in applied machine learning, and they are the ones tutorials skip because tutorial datasets arrive clean. For classmates, this is a reference to keep open during a project. For an employer, it demonstrates that I think about production reality — maintenance, monitoring, and the cost of different kinds of error — and not only about getting a model to train.
